# Mobile Banking 关键设计决策

本文记录系统当前阶段的重要架构选择、采用原因、约束条件和后续演进方向。设计决策以账户资金正确性、业务可追踪性和运行可维护性为主要目标。

## DD-001：采用模块化单体架构

### 决策

账户、转账、风控、审计和对账模块部署在同一个 Spring Boot 应用中，核心数据存储在同一个 MySQL 数据库中。

### 原因

- 账户余额、交易订单和账务流水可以由本地事务统一提交；
- 核心记账链路不存在跨服务远程调用；
- 部署、调试和故障定位更直接；
- 模块仍通过清晰的包边界和服务接口隔离。

### 约束

随着团队规模、数据规模和外部系统数量增长，需要重新评估通知、风控和对账模块是否异步化。账户记账核心不应仅为了拆分而引入分布式事务。

## DD-002：使用 BigDecimal 与 DECIMAL 表示金额

### 决策

Java 使用 `BigDecimal`，MySQL 使用 `DECIMAL(19,2)`。

### 原因

二进制浮点数无法精确表示许多十进制金额。金额模型需要明确精度、小数位和舍入规则，并在应用校验和数据库字段之间保持一致。

### 约束

当前系统只支持两位小数的 CNY 金额。扩展到不同币种时，应为币种配置最小货币单位和小数位规则。

---

## DD-003：使用数据库行锁保护余额更新

### 决策

转账执行时使用 `SELECT ... FOR UPDATE` 锁定付款账户和收款账户，并按账户主键固定顺序加锁。

### 原因

- 锁与数据库事务具有相同生命周期；
- 应用进程异常退出后数据库会自动释放锁；
- 多应用实例仍会对相同账户行形成互斥；
- 固定加锁顺序可以降低相反方向转账造成死锁的概率。

### 约束

高并发热点账户会形成锁竞争。后续可以评估账户分片、排队记账或专用账务引擎，但不能牺牲余额一致性。

## DD-004：幂等由应用语义和数据库约束共同保证

### 决策

每笔转账要求客户端提供 `Idempotency-Key`，系统保存规范化请求的 SHA-256 摘要，并建立付款账户与幂等键的唯一约束。

### 原因

- 唯一约束是并发场景下的最终防线；
- 请求摘要可以区分安全重试和错误复用；
- 已完成请求可以直接返回原业务结果；
- 客户端超时重试不会造成重复扣款。

### 约束

幂等键必须限定长度和字符集。外部支付渠道接入后，还需要建立渠道订单号和回调事件的独立幂等约束。

---

## DD-005：每笔转账生成双边账户分录

### 决策

成功的行内转账生成付款账户 `DEBIT` 分录和收款账户 `CREDIT` 分录，并记录交易前后余额。

### 原因

- 支持客户账单展示；
- 支持交易问题回溯；
- 支持根据期初余额和流水重新计算当前余额；
- 避免系统只保存余额快照而缺少变化依据。

### 约束

当前分录属于账户子账，不等同于完整会计总账。完整总账还需要会计科目、清算账户、会计日期、分录批次、关账和冲正流程。

---

## DD-006：使用不透明访问令牌

### 决策

登录后生成安全随机令牌，客户端持有令牌原文，数据库只保存令牌摘要。

### 原因

- 可以立即撤销当前会话；
- 用户禁用或权限变化可以由服务端即时生效；
- 数据库泄露时不会直接暴露可用令牌；
- 会话管理和审计边界清晰。

### 约束

每次认证需要访问会话存储。规模增长后可以增加短期缓存，但撤销和过期语义必须保持一致。

---

## DD-007：Redis 不参与资金正确性的最终判定

### 决策

Redis 当前用于登录失败次数限制等可替换能力。余额、订单状态、流水和幂等最终约束均由 MySQL 保证。

### 原因

资金链路只依赖一个一致性系统，可以减少数据库事务与分布式锁租约、网络分区之间的故障组合。

### 约束

Redis 不可用时可以关闭共享登录限流，或退化为单实例内存统计。若未来将非核心状态放入 Redis，需要明确缓存失效和降级策略。

---

## DD-008：订单先落库，再执行资金事务

### 决策

转账请求首先创建 `PROCESSING` 订单，随后在独立资金事务中锁定订单和账户、更新余额、写入流水并完成订单。

### 原因

- 每次业务尝试都有明确记录；
- 服务中断后可以识别悬挂订单；
- 失败原因和恢复过程可以审计；
- 余额和流水仍在单个资金事务中原子提交。

### 约束

恢复任务需要扫描超时的 `PROCESSING` 订单。多实例部署时，定时任务必须通过外部调度或租约机制保证互斥执行。

---

## DD-009：对账使用一致性快照

### 决策

对账在 `REPEATABLE_READ` 事务中读取账户余额并汇总流水。

### 原因

若账户查询和流水汇总看到不同提交时点，可能产生暂时性的假差异。一致性快照使单次对账基于同一数据库视图。

### 约束

当前为全量账户对账。数据规模增长后，应增加业务日期、分片、增量范围、批次重试和差异工单。

---

## DD-010：数据库迁移由 Flyway 管理

### 决策

所有表结构通过版本化 SQL 迁移创建，应用启动时验证迁移状态。

### 原因

- 避免依赖人工建表；
- 保证不同环境的数据库结构一致；
- 迁移历史可追踪；
- CI 可以在真实 MySQL 环境中验证迁移和实体映射。

### 约束

正式环境应分离迁移账户和应用运行账户，并在部署前完成迁移备份、回滚和锁表风险评估。
